# 登录、核验与恢复加固：schema 19–24

这是单人独立部署的应用层加固。应用内验证器、各供应商账户的双重验证和独立安全审计分别设置与验收。

## 管理登录

维护页提供 TOTP 验证器绑定。添加密钥后，先另外保存 10 个一次性恢复码，再输入有效的 6 位动态码并确认保存，才会启用。准备过程中原登录保持可用；绑定 10 分钟后过期。关闭或重新绑定要求口令与新的动态码／未使用的恢复码。不要把恢复码和管理口令放在同一个位置。

启用后，所有登录入口都要求第二重验证，包括兼容表单与 Bearer 入口。先向 `POST /api/session` 提交 `admin_token` 与 `mfa_code`，再使用返回的 30 分钟会话 Cookie 或 Bearer 会话。TOTP 与恢复码原子消费，拒绝重复使用。启用／关闭会撤销旧会话，并尝试向本人发送变更通知。

TOTP 秘钥使用独立内容密钥加密；恢复码以认证散列形式保存。恢复完整 schema 19–24 备份会保留已经启用的 MFA；需要对应的内容密钥。恢复码的认证散列还依赖原管理口令配置，更换部署管理口令后应重新绑定、生成新的恢复码。恢复后请重新登录。

schema 24 的内容密钥分页迁移覆盖已启用／待绑定 MFA、信件、旧 PDF、私人 PDF 分块、后台密文作业和认证清单。必须分别继续 `cursor`、`artifact_cursor`、`job_cursor` 与 `manifest_cursor` 四个游标，直到无剩余页、无冲突，并在新密钥隔离恢复中核对 MFA 后才能移除旧密钥。详见 [运维步骤](OPERATIONS.md)。

标准：[RFC 6238](https://www.rfc-editor.org/info/rfc6238/)。绑定和恢复策略参考 [OWASP MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)。

## 联系人核验

新网页核验必须通过保存在该联系人资料里的邮箱取验证码；提交任何状态（包括“误报”）都需要当前链接和对应邮箱验证码。代码为 8 位，10 分钟有效，最多 5 次尝试，只能消费一次，并绑定联系人、当前链接及轮次。重新取码会使上一份代码失效。链接默认 7 天；过期入口需要通过邮箱取码重新证明身份。本人的签到、旅行暂停、联系人停用／邮箱修改、链接轮换使旧轮次不可用。

取码每个联系人 5 分钟最多 3 次，所有验证码每天最多占配置发信额度的一半（最少 1 封），D1 原子领取。失败及结果不明同样占预留额度，防止反复取码吃掉全部发送预算。高确认人数需要足够的邮件额度，或使用已认证的 Gmail 回复路径。服务缺失、dry-run、发送失败或结果不明均不跳过验证。

Gmail 回复继续要求真实来源、当前联系人／线程／轮次、明确的首行指令、非引用内容及消息去重。网页和 Gmail 记录回复后，尝试通知本人及本轮其他确认人；通知共享全局每日发信上限，入箱和阅读取决于邮箱服务及收件人的实际处理时间；零缓冲可立即进入释放。邮箱账号失守仍可能冒用该联系人。

误报取消在 D1 事务中检查预期轮次，取消操作仅作用于预期轮次；新轮次和实际本人签到记录保留原样。

## 限流与告警

Cloudflare 原生绑定分别限制登录／MFA、核验、高开销操作、普通管理 API 和阅读／公开健康接口。普通 API 120 次／分钟，阅读链接 60 次／分钟；登录 10 次，核验及高开销入口 30 次。缺少绑定会拒绝请求；有界内存 fallback 只能由开发环境显式启用，部署检查不允许它。准确的全局发信额度由 D1 原子领取控制。[官方说明](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)

异常认证、429 和服务错误按种类、UTC 小时聚合，每个 isolate 每种错误每分钟最多记录一次，保留 7 天；该记录提供运行事件的采样汇总，详细诊断需结合维护记录。Cron 对服务故障、较多异常认证／限流、收信或投递故障尝试发送本人告警，每类每日去重。没有保存口令、链接令牌、请求正文或客户端地址。邮件或 Cron 自身不可用时，应依赖外部健康监控。

## 整份备份加密

新管理页的完整备份和资料导出默认在浏览器里加密后下载，备份口令在本机浏览器中用于加密。schema 24 的完整恢复格式 2 只保存一份规范恢复表，避免重复导出显示副本。联系人、公开草稿、私人密文和 PDF 都属于敏感备份数据。

新加密封套 2 使用 AES-256-GCM 的 1 MiB 认证分块；总长度、块数、块序号与格式头参与认证，删除、调换或替换块会失败。PBKDF2-SHA256 固定 600,000 次迭代，随机 16 字节盐；每块使用独立派生 nonce。兼容读取旧封套 1。明文上限 256 MiB，分块减少加密临时内存，但完整 JSON 与结果仍占内存。备份口令至少 12 字符，并应与内容密钥分别保管。

旧版/API 的授权导出仍提供原始 JSON，完整导出仍要求近期重新验证；API 使用者应运行 `npm run backup:encrypt -- RAW.json NEW-encrypted.json`。CLI 从 `AFTERME_BACKUP_PASSPHRASE` 读取口令，不打印口令，不覆盖文件，不删除原文件。

`backup:verify` 和离线恢复支持 schema 16–24 的完整明文及加密备份。必需表、单例配置、冻结规则、引用及密文均会检查，schema 22 PDF 分块还校验长度与摘要；恢复后的设置、目录、正式内容读取和数据库完整性检查通过才报告成功。加密备份需提供 `AFTERME_BACKUP_PASSPHRASE`，私人密文／MFA 还需要原内容密钥。恢复默认暂停释放，关闭公开页、撤销私人链接并建立新轮次，保留实际本人签到时间，在本机生成恢复数据库。

正文保存与 PDF 准备是不同状态。默认由已认证浏览器生成、分块上传，Worker 校验后交付；PDF 完整校验通过后标记就绪。旧执行模式的公开 PDF 源数据预检上限为 4 MiB，单份 PDF 默认上限为 8 MiB；schema 24 分阶段模式分页读取源数据，文件容量须按实例验收配置。Cloudflare CPU 与真实邮件送达在实例中分别验收，详见 [后台任务](BACKGROUND_EXECUTION.md)。

KDF 选取参考 [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。备份加密保护下载文件；普通信件由持有内容密钥的服务端解密投递。浏览器与部署账户属于数据的信任边界。

## 尚需部署者完成

- 在自己的验证器完成 AfterMe 绑定，另行保管恢复码；由本人独立保管第二因素。
- 在 Cloudflare、邮箱和代码托管账户启用第二重验证，保存各自的恢复方式。
- 将经过离线验证的加密备份及独立密钥复制到分开的可靠位置。
- 如需独立安全审计，委托第三方检查认证绕过、网页注入、邮件真实性、并发释放和部署权限。将第三方审计结果与本轮自动测试、自查记录分别保存。

已发送的邮件附件无法撤回。单人确认、零缓冲、第三方服务故障和未知漏洞仍是需要理解的运行边界。
